## Concrete P2 findings assigned for follow-up

### WA-01 — Combine status filtering with the job-list search

At the reviewed snapshot, a technician with many completed and Draft jobs cannot select only Draft or only Completed while retaining a site/client/inspector query. Portal provides All/Draft/Completed independently from search; the native dashboard only groups all matching jobs. Add the same status values without changing schedule-first ordering inside the remaining results or hiding local/offline jobs. Verify combined query + status, clearing both controls, group counts, and an explicit no-match state.

Evidence: `portal/pages/InstallationsPage.tsx:21,27,78`; `src/screens/DashboardScreen.tsx:34,130`. Assigned to the forms parity agent after this finding; implementation status is not inferred from assignment.

### WA-02 — Preserve inspector name in cloud-browser summaries and search

An installation visible in the portal can be found by installer name there, but the mobile cloud browser cannot find it by that name before import. `RemoteInstallationSummary` drops the already-available `inspectorName`, and its search omits that value. Preserve the camelCase/legacy alias at the existing read boundary and include it in search; no API/schema change is required. Local Dashboard already searches `inspector_name`.

Evidence: `portal/pages/InstallationsPage.tsx:30`; `src/repositories/remoteInstallationsRepository.ts:99`; `src/screens/RemoteInstallationsScreen.tsx:61`. Verify canonical and legacy mapping, empty inspector values, case-insensitive matching, and no mutation of the remote source. Assigned for follow-up; no fix claimed here.

### WA-03 — “Today” must identify the technician's work date

`schedulerRouteLocalCalendarDate` deliberately returns the device calendar date. DailyRoute uses it both initially and for Today, while the explanatory text says the saved technician timezone defines the work date. The API uses `globalUsers.timezone` to select jobs. When the device and technician dates differ, tapping Today can request yesterday's/tomorrow's assigned jobs relative to the saved work timezone. For example, at 01:00 UTC on September 5, Phoenix is September 4 while Sydney is September 5. This affects the connected-device Australian-address fallback particularly clearly.

Evidence: `src/domain/schedulerRoute.ts:37`; `src/screens/DailyRouteScreen.tsx:84,329,455`; `API/services/schedulerRouteService.ts:295,314`. Portal starts with an explicit blank date (`portal/pages/RoutePage.tsx:90,274`). Use the actual authenticated saved-timezone contract if available; otherwise match the portal's explicit-date flow rather than inventing the technician timezone from the device, GPS, installation, or address. Verify a cross-date-zone case and calendar/DST arithmetic, while keeping manually selected dates unchanged. Assigned for follow-up; this audit did not establish an initial mobile profile timezone source.
